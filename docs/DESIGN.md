# Favecus Player の構造

## v0.7.0：iOS版・同期の方針と共通データ仕様（Step1）

本節は設計の確定であり、コードは変更していません。実装はStep2以降です。「ユーザー確認待ち」は推奨案であり、確認までは実装に入る前提としません。

### 層と配置

- `src/`（Windows版）は移動しません。端末非依存の共通JS（library-data / library-identity / media-identity / library-share / import-identity / queue / urls / library-tree / library-search 等）を規則の正本とします。
- `shared/spec/`（スキーマ）と `shared/fixtures/`（期待値付きの共通テストデータ）を追加し、NodeとiOSの両方で同じデータを実行して仕様のずれを検出します。
- iOSは `ios/`（XcodeGenの `project.yml`、App / Features / Domain / Platform の層）に置きます。保存・通信・再生・認証はPlatform層でネイティブ実装し、データ規則はDomain層がJavaScriptCoreの共通JSまたはSwift再実装（共通テストデータで一致保証）で担います。
- JavaScriptCoreで実行する範囲は構造検証・階層・識別・検索・共有形式・同期のマージです。`library-data.cjs` が `require('../ui/library-tree.js')` で別ディレクトリを参照しており、JavaScriptCoreには `require` がありません。束ね方（単一ファイルへのバンドル）をStep3で決めます。`atob`・`TextEncoder` 等がJavaScriptCoreで使えるかは主張せず、Step3で実機相当のシミュレーターで検証します。

### 識別：MediaKeyを端末間の正本にする

- 名称：既存の `media-identity.cjs` の `MediaKey()`（正規化URL＋パートの照合キー）と区別するため、同期用の文字列を**SyncMediaKey**と呼び、同期レコードのフィールド名は `syncKey` とします。SyncMediaKeyは `MediaKey()` の結果（確認済みav/BVの対応後の代表URL＋パート）から導出する純粋な変換で、Step4で実装します。以下「mediaKey」と書いた箇所はこのSyncMediaKeyを指します。
- **端末間の同一性はSyncMediaKeyで決めます。mediaIdは端末内の参照用に留めます。** 同期しても読み込み規則（照合キーとmediaIdが一対一。DESIGN上の既存規則）を破らないためです。別端末が同じBV＋パートを独立に登録するとmediaIdが異なるので、同期では次のとおり扱います。
  - 同期レコードには `mediaKey` を持たせ、受信側はmediaKeyが既存の登録と一致すれば**自端末のmediaIdを使い、受信側のmediaIdは採用しない**。一致しなければ受信側が新しいmediaIdを割り当てます。この対応は端末ごとの表に保持し、同期レコードには端末のmediaIdを含めません。
  - これにより、マージ結果が一対一規則に違反して起動を止めることを防ぎます。
- MediaKeyの形式（v1）：`bili:<BV>:p<パート>`。CIDは保存せず、確認済みメタデータとして任意に保持します。
- av番号のみで確認済みBVがない登録の仮キー：`bili-av:<aid>:p<パート>`。通常APIでav/BVの対応が確認されたとき `bili:<BV>:p<パート>` へ昇格し、昇格は「旧キー→新キー」の変更レコードとして同期します。受信側は旧キーと新キーを同一として扱います。この昇格レコードは実質的にav/BV対応の同期なので、下記の判断2に従います。判断2が否決された場合、各端末は自分で対応を確認した後にだけ昇格し、受信した昇格レコードは確認まで保留します。
- ローカル曲：識別は端末内のfileNameのまま、内容ハッシュによる同定は既存方針どおり行いません。他端末では `mediaIncluded:false` の取り込みと同様に**未充足参照**として表示します。ZIPで実体を取り込んだ場合のみ充足します。
- **videoAliases（av/BV対応）の同期**：現行方針は「外部のaliasesを取り込み先の確認済み対応表へ登録しない」です。同一アカウントの他端末が確認した対応は、同期経由に限り**確認済みとして受け入れる**案とします。これは現行方針の変更であり、受け入れた対応は一対一・矛盾拒否の既存検証を通し、矛盾する場合は受け入れず通知します。ZIPと他者の共有ファイルには従来どおりこの変更を適用しません。**（ユーザー確認待ち。推奨：同期経由のみ受け入れ）**

### 保存形式と移行

- 同期用の追加情報は、既存JSONの `identityVersion` を上げず、独立した `syncVersion`（初版1）として別ファイル `sync/state.json` に保存します。既存JSON（version 3 / identityVersion 2）は変更せず、導入時に `library.pre-0.7.0-*.json` へバイト単位で原本を保存します。バックアップできなければ同期を有効にしません。
- 未知の `syncVersion` は、旧版へ戻して上書きせず同期を停止します（既存の未知identityVersionの扱いと同じ）。
- 同期をオフにしたままの端末は、従来どおり単独で動作します。

### 同期レコード

変更単位の追記型とし、状態全体を送りません。レコードの種類は次のとおりです。

| 種類 | 識別 | 主な内容 |
| --- | --- | --- |
| playlist | playlistId | 名前、アイコン参照、参加フラグ、削除状態 |
| edge | (parentId, childId) | 並び順キー。最上位は擬似親 `ROOT` からの辺として表す |
| track | trackId（登録曲id） | 所属playlistId、mediaKey、曲名、元URL、パート、並び順キー、削除状態 |
| mediaAlias | (aid, bvid) | 確認済みav/BV対応 |

各レコードは `hlc`（下記）、`deviceId`、`deleted` を持ちます。実体（MP4/M4A）、端末の絶対パス、一時ファイル、Bilibiliの認証情報は含みません。同じ子リストを複数の親が持つ共有子リストは、単一のParentIdではなく**辺の集合**で表し、情報を失いません。

### 時刻・並び順・競合

- 時計はHLC（ハイブリッド論理時計）とし、端末の壁時計を信頼しません。HLCが同じときは `deviceId` の辞書順で決定します。
- 並び順キーは分数インデックス（挿入間に文字列キーを生成する方式）とし、同一位置への同時挿入は `(キー, hlc, deviceId)` で決定的に整列します。キーが長くなりすぎた場合は、その親の辺だけを再採番する変更レコードを送ります。
- 同一フィールドの競合は最新のhlcが勝つ（フィールド単位のLWW）。削除と更新の競合は削除が勝ちます。削除済みの辺・リストを復活させるのは、新しいhlcを持つ明示的な作成レコードのみです。
- **循環**：各端末では局所的に正しい二つの移動を両方適用すると循環する場合があります。マージ後に循環を検出したら、循環を作った辺のうち hlc が最大のもの（同値ならdeviceIdが大きいもの）を**無効化**します（削除済みの辺を復活させません）。その結果、子に生きた親が残らなければ子を `ROOT` に付けます。決定的に同じ結果になることを共通テストデータで確認します。
- **親の削除**：削除は辺と playlist 自身にだけ付き、子へ連鎖しません。他に親を持つ共有子リストは残ります。生きた親がなくなった子は `ROOT` に付け、曲を失わせません。
- **削除されたリストの曲**：リストのTombstoneより新しいhlcを持つ登録曲（削除後に他端末がオフラインで追加したもの）は、黙って削除せず、`ROOT` 直下の復旧用リスト（名前は「復旧」、競合として通知）へ移して保持します。Tombstoneより古い曲はリストとともに削除します。
- **上限999個**：マージ後の総数が999を超える場合は、受信したplaylistを `(hlc, deviceId)` 順に並べ、**全端末で同じ先頭N件だけを適用**して残りを保留キューに置き、ユーザーへ通知します（保留する端末同士が互いに異なる集合を保留して収束しないことを防ぐため）。保留したリストに依存する辺・登録曲のレコードも保留します。起動を止める状態の書き込みは行いません。
- 登録曲の上限10000件も同じ規則で保留します。

### 既存JSONとの変換・初回同期・書き込み順

- **変換**：`childIds` と `rootPlaylistIds` の配列順を、親（最上位は `ROOT`）ごとの辺レコードへ変換し、順序に等間隔の初期並び順キーを付けます。登録曲の配列順も同様に並び順キーへ変換します。初期hlcは変換時点の物理時刻とカウンタ0にdeviceIdを付けたものとし、同一内容を再変換しても同じレコードIDになります。逆方向（同期状態→既存JSON）は並び順キー・hlc順で配列へ戻し、変換→逆変換で階層・順序・IDが一致することを共通テストデータで確認します。
- **正本**：`library.json`（既存）を表示・再生の正本とし、`sync/state.json` は同期の補助（outbox、保留キュー、hlc、Tombstone）です。
- **書き込み順**：変更はまずoutboxへ追記して確定し、その後 `library.json` へ反映します。受信側は適用を（レコードID＋hlc）で冪等にし、途中で停止しても未送信の変更を失わず、同じ変更を二重に適用しません。再起動時はoutboxの未反映分を `library.json` へ再適用します。
- **初回同期**：同じplaylistId/登録曲idは同一レコードとして統合します（Windows版のZIPをiPhoneへ取り込み、IDが保たれている場合）。互いに独立して作られたライブラリは、IDが異なれば別物として併存し、同一syncKeyの登録曲はmediaIdだけを共有して登録行は別々に残します（名前の重複は既存の取り込み用接尾辞で区別）。自動で統合・削除しません。
- **ID形式の確認（Step4の前提）**：現行の `library-data.cjs` はリスト/登録曲idがUUIDかを検証していません。pre-0.5.0からの移行データに短い独自IDが残っている場合、独立した二つのライブラリで衝突して無関係なリストが統合される恐れがあります。Step4で既存データのID形式を確認し、UUID以外があれば同期の有効化時に原本を保護して新しいUUIDへ付け替える手順（既存の取り込みの再割当と同じ対応表方式）を定義します。

### Tombstoneと長期オフライン

- 削除はTombstone（`deleted:true`）で表し、古い情報による復活を防ぎます。保持期間の推奨は90日です。**（ユーザー確認待ち）**
- 保持期間を超えて同期していない端末は、差分ではなく全量再同期とします。そのとき端末側の未送信の変更は、競合として一覧にして確認します（黙って上書き・復活させません）。

### ローカルDBと同期キュー

- 操作は先にローカルDBへ反映し、同期キューへ積み、通信可能時に送ります。オフラインでも閲覧・編集・並び替え・保存済み再生ができます。
- 保存や同期が途中で失敗しても、中途の状態を確定扱いにしません。再起動後は最後に確定した状態から再開します。

### DeviceMediaと保存状態

- DeviceMedia（端末ごとの保存情報）は、mediaKey、形式（動画/音声）、画質、保存状態、端末内パスを持ち、**同期しません**。
- 状態：NotDownloaded / Preparing / Downloading / Processing / Validating / Completed / Failed / Cancelled。Windowsの既存カタログ（layout 4）はCompletedに相当します。再起動後、Completed以外のファイルは完成扱いにしません。サムネイルの失敗で本体を削除しません。

### ZIPの拡張

既存のFVPA0002（内側のidentity.json、shareVersion 1）は維持し、`manifest.json` にmediaKeyの一覧を追加します（shareVersion 2案）。旧ZIPは従来の互換経路で読み込みます。新ZIPを旧版アプリで読めることは保証しません。ZIPはバックアップ、手動移行、メディア共有に残し、削除しません。

### 認証情報

Windows：Electron safeStorage。iOS：Keychain。平文保存、ログ、同期、ZIPへの出力は行いません。取得できない配信は「取得不可」で終え、保護・制限の回避は実装しません。

### 外部ツールの責務

署名・導入・更新はAltStore Classic／AltServer／iOSショートカットに任せ、FavecusPlayerは署名制限の回避処理もAltStoreの内部状態の取得も持ちません。App IDは10個まで（各1週間）でアプリの拡張機能ごとに消費されるため、**iOS版はApp拡張（Share Extension等）を持たない**制約とします。Step10の共有シート/Filesからの取り込みは、書類タイプの登録と「このアプリで開く」で実現します。AltStore自体が有効アプリ3つの枠を使うかは公式ページで未確認です（Step2・16で実機確認）。

## v0.6.7開発中：共通識別と端末処理の境界

`media-identity.cjs` はURL正規化、動画・パートの識別、確認済みav/BV対応、動画/音声の保存識別を扱う純粋な処理です。依存先は同じく端末非依存の `urls.cjs` のみです。ファイル・通信・Electron・時計・乱数には依存しません。識別規約のバージョンは `IDENTITY_VERSION = 1` です。これは保存JSONのversionやアプリのバージョンとは別です。

- `VideoIdentity(input, details)`：URLの追跡情報を除き、パートを残します。同じメタデータのaid/bvidの両方が妥当で、その一方が入力動画と一致する場合だけBVを代表URLにし、av/BVの両URLを返します。aidが数値なら安全な整数のみ受け付け、大きなIDは桁を保つ文字列で扱います。対応情報がない・入力と異なる・不完全な場合は別動画のままです。実通信は呼び出し元のアダプターで行い、この関数自体がAPIの内容を照会・認証するものではありません。
- `MediaKey`：曲名、リスト名、所属、登録曲IDに依存しない照合キーです。メタデータなしでは従来のキーをそのまま返します。ローカル曲の照合は端末内の既存fileNameで行い、永続的な参照はmediaIdで保持します。共有時はStep1-3-2の衝突処理に従ってmediaIdを維持または再割当します。
- `DownloadIdentity`：動画と音声を区別します。メタデータを指定しない場合のキーは従来の「正規化URL＋改行＋形式」と一致します。画質は同じ保存対象の選択条件として引き続き別管理します。
- `SameVideo`：再生中のURL確認にも同じ対応判定とパート区別を適用します。別の動画のメタデータだけを根拠にナビゲーションを許可しません。

追加時の照合と重複候補判定、保存キーのSHA-256入力、ダウンロード解決時の別表記、再生中URLの照合をこの共通処理へ接続しています。保存カタログのキーは保持し、保存パスの移行は後述のStep3-1の手順に従います。登録曲IDとメディアIDは分離しました。確認済みav/BVの対応表を永続化し、同じパートのmediaIdを共有します。共有先とのID衝突処理は次節の取り込み方針に従います。

| 境界 | 現在の担当と次の整備 |
| --- | --- |
| 共通の構造・順序・検索 | library-tree.js / library-search.js / queue.cjs。親子グラフ・登録曲検索・再生順をUI・端末処理から分離して扱います |
| 共通の識別 | urls.cjs / media-identity.cjs。ファイル名や画面表示から動画を同定しません |
| 永続化 | library-data.cjsが共通検証、store.cjs がNodeのファイルI/OとUUID生成を担当。既存JSONはversion 3を維持し、identityVersion 2でmediaIdとvideoAliasesを保存します。割当計画は純粋なlibrary-identity.cjsで行います |
| ネットワーク・実保存 | bilibili-download.cjs / download-fetch.cjs / download-transfer.cjs / offline-library.cjs がメタデータ取得、ハッシュ、保存先、カタログ、FFmpegを担当します |

## メディア識別の保存形式（Step1-2 / Step1-3-1）

保存JSONの階層形式は `version: 3` を継続し、メディアID形式の識別にルートの `identityVersion: 2` を用います。Step1-2のidentityVersion 1も読み込んで移行します。各登録曲は従来の `id` に加えてUUID形式の `mediaId` を持ちます。IDの生成・ファイル保存はStoreが担当し、library-identity.cjsは既存IDの整合性確認と新規割当の計画のみを行います。

- プレイリストのid、登録曲のid、親子関係、順序、設定、メディアのfileName・保存パスは移行で変更しません。
- 正規化された同じBilibili URLとパート、または同じ取り込み済みローカルfileNameを参照する登録曲はmediaIdを共有します。曲名・所属先・端末の絶対パスをIDに含めません。確認済みav/BVの永続的な対応付けは、次節のvideoAliasesから解決します。
- コピーは登録曲idを新しくし、mediaIdを保持します。移動は最初の新規移動先に登録曲idを引き継ぎ、追加の移動先は新しい登録曲idを持ちます。移動先に同じ曲が既にある場合は既存の登録曲idを優先します。
- ローカル曲を改めて取り込む場合は別のファイル参照とmediaIdを作ります。内容のハッシュによる同定は行いません。最後の登録を削除後にURLを再登録した場合も新規mediaIdです。削除履歴や端末間での同一性は後続の同期仕様で扱います。
- 同じ照合キーに異なるmediaId、または異なるキーに同じmediaIdがある保存データは読み込み・保存を止めます。未知のidentityVersionも、旧バックアップへ戻して上書きせず停止します。新形式でmediaIdが欠けている場合も勝手に作り直しません。
- 旧version 3でidentityVersionがない場合、またはidentityVersion 1の場合は、移行前のJSONをlibrary.pre-0.6.7-*.jsonにバイト単位で保存してから追加します。さらに古いversion 1/2は既存のlibrary.pre-0.5.0-*.jsonを保持します。バックアップできなければ移行しません。
- 保存は新規一時JSONを書き、通常バックアップを保管してから本体を置換します。mediaIdは置換成功後にメモリ上の登録曲へ反映します。操作中の保存失敗は既存のロールバックで元の状態を戻します。

共有JSONはversion 3にidentityVersionとvideoAliasesを含めます。ZIPは従来のFVPA0002（明示パスワード指定時はFVPA0001）の内側へidentity.jsonを加え、同じ識別形式を保持します。identity.jsonのない旧ZIPと、識別形式のない旧JSONも読み込めます。新ZIPを旧版アプリで読めることは保証しません。情報のみ/DL同梱の出力分離は後述のStep3-2の共有形式に従います。

## 確認済み動画の対応情報（Step1-3-1）

identityVersion 2の保存JSONは `videoAliases: [{ aid: "123", bvid: "BV..." }]` を持ちます。aidは桁を保つ文字列です。対応は動画単位で保持し、各曲のパート番号は別に照合します。表は一対一、最大10000件とし、矛盾・不正形式を拒否します。

- Store.RememberVideoは入力のav/BVと一致する通常APIのaid/bvidが揃う場合だけ対応を追加します。未確認の推測変換や、外部ファイルのaliasesだけによる登録は行いません。
- 再生用メタデータの取得、URL追加時の曲名取得、通常ダウンロード/画像取得のアダプターから接続します。外部APIを利用しない共通モジュールが対応表を検証し、Storeが保存します。保存できない場合は通知し、元の表とmediaIdへ戻します。
- 初めて同一と分かった曲のmediaIdは、保存済みプレイリスト・登録順で最初に現れるIDへ統合します。登録曲id、各行、曲名、元URL、パート、階層と並び順は変更しません。既に同じ対応が保存済みなら再保存しません。
- 通常読込と保存では、対応表による正規化後のキーとmediaIdが一対一か確認します。明示的な確認・統合以外で矛盾したIDを黙って直しません。
- 再起動後の追加・重複候補・移動先の照合でも同じ対応表を使います。追加の確認中に対応表が変わった場合は再確認が必要です。
- 既存DLカタログのハッシュと再生回数のキーは保持します。保存パスはStep3-1で原本保護と再開記録を伴って移行します。共有形式のID維持・衝突処理は次節に記載します。

## 共有IDと取り込みの衝突方針（Step1-3-2）

import-identity.cjsは検証済みのリスト・ルート一覧と移入先の現在の状態から、新規追加分のIDを計画します。ファイル操作は行わず、入力を変更しません。JSONのStore.ImportもLibraryArchiveの検証・計画・確定へ集約します。

| ID・参照 | 処理 |
| --- | --- |
| 新形式のリストid・登録曲id | 未使用なら維持。既存のリストまたは登録曲idと衝突した分は再割当し、childIds・rootPlaylistIds・選択先も同じ対応表で変更 |
| 既存の同一メディア | 移入先の正規化キー（確認済みav/BVとパートを含む）で一致すれば移入先のmediaIdを優先 |
| 未使用の外部mediaId | 移入先で別メディアに結び付いていなければ維持 |
| 別メディアに使用済みの外部mediaId | 新しいmediaIdへ再割当。IDだけを根拠に動画を統合しない |
| ローカルファイル | 新しいfileNameで別途配置。同じ外部ファイルを指す複数の行は1回だけコピーし同じmediaIdを共有。既存ファイルの内容は変更しない |
| 識別情報のない旧形式 | 従来どおりリスト/登録曲idを新規割当。mediaIdは移入先のキーから割当 |

- 取り込みは新しいリストの追加です。IDが一致しても既存リストの内容・名前・順序を上書きしません。追加分の名前が重複する場合は既存の取り込み用接尾辞を使います。自動同期や更新取り込みではありません。
- 外部videoAliasesはソース内のID整合性確認のみに使用し、移入先の確認済み対応表へ登録しません。移入先でまだ確認できないav/BVに同じ外部mediaIdが付いている場合は、それぞれのURL/パートへ分けて割り当てます。通常APIで確認後にRememberVideoが統合します。
- ZIPの一元的なidentity.jsonとJSONのルート情報から、未知形式、IDの欠落・矛盾、階層の不正をファイル配置前に検証します。選択取り込みでも空の祖先と親子順序を維持します。
- ローカルメディアはステージング領域に展開・検証し、排他的に配置できたファイルだけを今回の所有物として記録します。既存の同名ファイルが現れた場合は上書きせず中止し、その既存ファイルを後片付けで削除しません。
- 最終保存に失敗した場合はメモリ上のリストを戻し、新しく配置したメディアとDLカタログの段階変更を復元します。取り込みが待機中に別の編集が入った場合は取り込みを止め、並行した編集を保持します。

## 動画リンク単位のDL保存（Step2）

新しくDLするデータと既存のDL同梱取り込み経路の新規配置は、`layout: 4` として `downloads/media/<動画ID>-p<パート番号>/` に保存します。ファイルは動画/音声形式とUUIDを含む名前で排他的に配置します。プレイリスト名、曲名、所属する親の経路は保存先に含めません。

- 保存前にav/BVの対応が確認済みなら、代表のBVで曲フォルダーを決めます。既にlayout 4の正常なファイルがある場合はその曲フォルダーを優先し、後から対応が判明しても移動しません。
- 動画・音声は同じ曲フォルダーを使います。同じパートの正常なサムネイルは両形式から同じファイルを参照し、余分な画像取得を避けます。壊れた画像は再取得できます。
- Findと保存状態一覧は、カタログ内の別表記に加え、Storeの確認済み対応表も参照します。元のカタログキーがavでもBVから保存済みデータを利用でき、パート違いは区別します。
- 画質を変える場合も曲フォルダーと既存カタログのtoken/urlを維持し、同じ形式の新しいファイルへ置き換えます。確認後に旧ファイルを片付け、別形式が使うサムネイルは保持します。
- 同時要求は、同じ保存形式の各URL・確認済みの代表キーで待機させます。別表記リストの全体が完全一致することに依存せず、重なりがある要求を直列化し、待機後に保存済み状態を再確認します。失敗・中断でも待機を解除し、全ワーカーの終了を待ちます。別の曲は従来どおり最大3件並列です。
- リスト名・曲名・親子関係の変更や所属の移動ではlayout 4の保存先を変更しません。既存の階層再整理処理もlayout 4を対象外とします。
- 書き込み失敗時は自分で作成できたファイルだけを片付けます。排他的配置で衝突した既存ファイル、またはカタログ内の別形式が使用中の画像は削除しません。

旧カタログのtoken、URL、index.json version 1は保持します。情報のみ/DL同梱の出力分離と、取り込み時のメディア照合は下記のStep3-2で接続しました。

## 既存DLデータの移行（Step3-1）

offline-migration.cjsが旧layoutなし/1/2/3の正常な管理対象をlayout 4へ移行します。起動時とDL開始前に呼び出し、親子階層への再配置は行いません。プレイリスト構造・登録曲・設定は変更しません。

- 最初に元のindex.jsonを排他的なindex.pre-0.6.7-UUID.jsonへバイト単位で保管します。バックアップに失敗した場合はメディアを変更しません。
- 1レコードごとに.layout-migration.jsonへ元レコード、移行先、SHA-256とサイズ、整理対象を記録します。コピー先を排他的に作成し、内容を検証してからindex.jsonを原子的に置換します。通信・再DL・形式変換は行いません。
- 起動後の再開ではバックアップと移行記録を照合します。検証済みのコピーは再利用し、管理情報の保存直後に中断した場合も既存の確定先を認識します。容量不足・権限不足・取消時は旧ファイルと記録を保持します。
- 元データの削除は確定先の内容確認後に限ります。全カタログで参照中の実体は保持し、旧ファイルの内容が変わっていれば削除しません。空ディレクトリだけを下から整理し、未知のファイルを含むディレクトリは残します。使用中などで削除できなければ記録を残して再試行します。
- 移行記録、カタログ、配置形式が不明な場合は保持して警告します。シンボリックリンクは移行しません。欠落・サイズ不一致のメディアと利用できないサムネイルの参照は保持します。
- 中断したコピーか外部ファイルか判別できない不一致の移行先は上書き・削除せず、新しいUUIDの保存先を選びます。この場合は判別できない残存ファイルが残ることがあります。バックアップと不明な実体を自動で一律削除しません。
- 移行は同じインスタンス内で一度だけ実行し、その間はDL開始、保存先変更、出力・取り込みを排他にします。保存一覧のメモリとディスク上の内容を照合し、並行変更された場合は、その変更を上書きせずに中止します。
- 確認済みav/BVと同じパートは既存layout 4のフォルダーを優先し、正常な画像を共用します。別パートは別フォルダーです。旧配置の同形式レコードが別表記で複数残る場合もtokenを保持し、内容・画質を推測して統合しません。

本工程の自動検証はプロセス中断・I/O失敗の模擬を含みます。電源断に対するストレージ全体の耐久性、Windows実機のファイルロックと実GUIは別途確認します。

## 出力方式と共有メディア（Step3-2）

共有構造はversion 3/identityVersion 2を維持し、shareVersion 1とexportMode（information/media）を加えます。未知の共有版・出力方式・矛盾した同梱宣言はファイル配置前に拒否します。旧JSONと共有方式の識別がない旧ZIPは従来の互換経路で読み込みます。

| 方式 | 出力とローカル曲の扱い |
| --- | --- |
| information | メディアとDLカタログを読み込まず、構造だけをJSONまたはZIPに出力します。ローカル曲はmediaIncluded falseを明示します |
| media | ZIPに構造、正常な保存済み動画・音声・画像、ローカル実体を同梱します。見つからないローカル曲はmediaIncluded falseで情報を残します |

- library-share.cjsは構造を検証して必要なフィールドのみを取り出します。プレイリスト/登録曲/mediaId、親子関係、順序、名前、正規化リンクとパート、日時、リスト画像などを保持します。設定・認証情報・端末の絶対パス・未知の追加プロパティを構造へコピーしません。リスト画像は既存の小型PNG形式を継続します。
- LibraryArchive.Export(file, password, { mode })が両方式を担当します。省略時は従来どおりmedia、informationでは.jsonと.zipを使用できます。ZIPの内側のidentity.jsonにも共有方式を記録します。JSONへのメディア同梱やパスワード指定は拒否します。出力先と同じ親に排他的な一時ディレクトリを作り、完成後に置換します。
- Store.Export(parent, { mode })は旧フォルダーJSON用の互換APIです。informationではJSONだけ、mediaではローカルsidecarも出力します。DL実体も渡す通常アプリの経路はOfflineLibrary付きのLibraryArchiveです。
- 同じローカルfileNameの同梱宣言は全登録で一致させます。falseの取り込みではsidecarや同名の移入先ファイルを探しません。既存のローカル参照と実ファイルに衝突しない新しいfileNameを割り当て、登録とmediaIdの衝突を従来方針で解決します。実体がない登録はSnapshotのmissingで判別でき、再起動・再出力でも情報を保持します。
- informationで省いたローカル曲はomitted、mediaで欠落した実体はmissingとして別に集計します。新ZIPのmediaIncluded trueに実体がない場合や、informationのZIPにメディア等が隠れている場合は拒否します。共有方式のない旧JSONでは従来のmedia/sidecar探索を継続します。
- DLカタログの共有情報はtoken・正規化URL/同パートの別表記・形式・サイズ・時間・画質と同梱先に限定します。元のPC保存位置、署名等が付く可能性のあるthumbnailURL、設定・未知のメタデータは出力しません。
- 取り込み先が確認済みの動画・パート・形式に正常な実体を持つ場合は、その画質と保存先を優先し再配置しません。欠けた形式だけを同じ曲フォルダーへ追加し、画像も共用します。参照を先に索引化してから配置し、同じメディアを登録曲ごとにコピーしません。
- 外部の対応情報はソース側の実体選択にだけ使います。取り込み先へ未確認のav/BV対応を登録せず、保存URL/aliasesは取り込み先の確認済み識別に合わせます。取り込み先で未確認の別表記がそれぞれ明示的に登録される場合は、別mediaId/保存参照として保持します。
- 実体は専用ステージへZIPのCRC・サイズを検証して展開し、排他的に公開します。衝突した別ファイルは削除しません。保存一覧のメモリ/ディスクの先行変更を検出し、保存後に失敗を報告された場合は実際のindex.jsonを読み返して復旧します。確定状態や復旧自体を確認できない場合は、参照がある可能性のある追加ファイルを残して停止します。
- 出力と取り込みは同じStoreとOfflineLibraryで排他にし、失敗後もロックを解除します。構造保存失敗時は従来どおり新規登録と配置を戻します。プレイリスト名の衝突時の接尾辞、移入先設定による曲名整理、ID衝突時の再割当は既存仕様を維持します。自動同期や既存登録の上書きは行いません。

ここまでの変更はコア処理です。画面の二つの出力ボタン、階層の選択・取り込み先UIはStep6で接続します。Windows実機での操作、実通信と全体ビルドは後続の所定工程で確認します。

## 参照と削除待ちデータの基盤（Step4-1）

Step4-1で基盤を整備し、Step4-2でmain.cjsのreferenceDataとStoreの確定通知へ接続しました。起動時と保存確定後、DL・出力/取り込み・利用終了後に、参照と使用状況を再確認して自動整理します。

- offline-cleanup.cjsが保存確定済みのversion 3ライブラリから参照集合を作ります。所属プレイリストや全体再生の対象設定にかかわらず全登録を数え、確認済みのav/BVは共通キー、別パートは別キーとして扱います。参照元が不明・未知・破損なら削除しません。
- Store.Save成功後に確定スナップショットと元JSONを保持し、任意のcommittedコールバックを呼びます。SavedDataは初回とファイルの識別・更新情報が変わった場合にディスクの内容と照合し、同じ保存結果の間は確認済みのスナップショットを再利用します。未保存の編集、保存失敗後のメモリ状態、外部から直接変更されたJSONを削除の根拠にしません。コールバックの失敗で成功済みの保存を取り消しません。
- 最後の参照がないカタログ項目は、物理削除に先立ちindex.jsonへcleanupVersion 1とcleanup配列を原子的に保存します。元レコードと対象パス、サイズ、デバイス/ファイル番号、変更時刻を残すため、使用中・権限不足・削除後の確定失敗でも再起動後に続行できます。削除待ち項目のない場合は従来のversion 1/files形式を維持します。未知の削除形式は原本を保持して読み込みを止めます。
- 画質更新などで以前のレコードを置換する場合も、参照判定が有効な構成では旧パスを同じカタログ確定で削除待ちへ登録します。現レコードから参照される実体と画像は削除しません。削除待ち中に同じ動画・形式が再登録され、別の正常な保存先がなければ、識別情報が一致する残存ファイルをカタログへ戻します。
- Pin(record)の解放関数で複数の利用者を数えます。最後の利用者が解放するまで関連ファイルの整理を延期し、解放は重複して呼んでも一度だけ反映します。Pin中は保存先変更を拒否します。DL・出力/取り込み・移行中と、未解決の移行記録がある場合も整理を待機させます。
- 削除直前に最新の確定参照と利用者、現在のカタログからのパス参照を再確認します。ディスク上のカタログが先行変更されていれば書き換えません。実体の識別情報が変わった場合、シンボリックリンク、元々存在しなかった位置に現れたファイルは保持します。削除対象はカタログと削除待ち記録にある実体だけで、ディレクトリを一律走査して削除しません。フォルダーは空の場合だけ除去します。
- 整理は1回100レコードずつ進め、残りは後続の処理へ渡します。使用中・権限不足のI/O失敗は削除待ちを残し、30秒後または利用終了後・次回起動時に再試行します。内容が変わった実体は自動で削除可能と見なしません。

### アプリ操作・再生/配信との接続（Step4-2）

- 単曲削除、リスト削除、追加、単曲/複数曲移動、対応表確認、取り込みなどの保存成功通知を共通の再判定へ接続しました。移動は保存確定後の参照で判定し、最後の参照がなくなったデータだけを整理します。ローカル取り込みの元ファイルはDLカタログとは別の扱いを維持します。
- DL済みの再生は、その時点のレコードと実パスを新しい再生画面へ固定します。画質更新後も旧画面が新ファイルへ切り替わらず、再生し直した画面だけが新しい実体を使います。停止要求とネイティブ画面の実際の破棄を区別し、destroyedまでPinを保持します。closeが失敗した場合も実際に破棄されるまで保持します。
- 再生画面ごとにランダムな経路IDを作り、local.jsから内部配信URLへ渡します。トークンと経路IDが一致する登録済み画面だけに配信し、破棄後の経路やIDのない要求は拒否します。配信開始時にも独立したPinを取り、読み取りストリームのcloseまで保持します。読み切り、取消、Abort、HEAD、404/416等で解放し、画面終了後も残っている配信を保護します。
- 移行の旧実体削除も、整理が有効な場合はcleanupキューへ委譲します。移行記録の元ハッシュに一致しなくなった実体はblockedで保持します。移行元と画像のPinが解放される前に直接削除しません。カタログ全体の先行変更も照合します。
- DL同梱取り込みでは既存cleanupを保持し、置換元のレコードを新カタログと同時に削除待ちへ入れます。書込み直後の例外と最終保存失敗の復旧では、共通のIndexValueによるカタログ全体とcleanupを確認・復元します。確定状態を確認できない場合は従来どおり実体を保持します。
- 整理で一覧や警告が変わった場合はdownloads状態を通知します。参照集合と使用パスの索引を再利用し、完了した削除待ち記録をバッチごとに確定します。保留した項目を同じ走査で繰り返さず、先頭に多数の使用中項目があっても後続を処理します。I/O失敗後の継続は30秒後の再試行へ渡し、失敗直後の連続書込みを避けます。
- 終了時には整理タイマーを破棄します。終了までに完了しなかったカタログ/cleanupの対象は次回起動時に再確認します。画面レイアウトやボタンの変更はなく、内部の再生URLとライフサイクルの接続を変更しています。

この工程の確認はNode上のファイルI/O、ストリーム、模擬Electronによるものです。実Electron/Windowsでのネイティブ終了・ロック・再生、Bilibili実通信はStep11の全体確認へ引き継ぎます。

## 編集画面からの単曲ダウンロード（Step5）

単曲DLは既存DownloadsDialogの対象指定を拡張し、プレイリスト保存と同じ見積もり・形式/画質・開始・中止・進捗・エラー処理を使います。対象はplaylistId・entryId・entryURLで保持し、単曲モードでは子リストを含めず、リスト選択を出しません。mainの共通対象解決で現在のStore.EntryとURL/パートを照合してから、1件だけをOfflineLibraryへ渡します。削除・移動・URL変更、不完全な単曲指定、ローカル曲や子リスト指定との混在は、リスト全体へ置き換えず拒否します。

編集の名前はDL画面を開く時点の入力として戻り先へ保持し、「戻る」と保存開始後に編集画面へ復元します。タイトルの保存は編集画面の明示的な保存だけで行います。DL画面を閉じる際は事前見積もりだけを中止し、開始済みの保存は従来のバックグラウンド進捗と中止操作で管理します。登録曲が変わった場合は古い対象で開始せず、再度編集を開くよう案内します。

カタログや保存先・再利用の方式は既存のOfflineLibraryへ委譲します。単曲ジョブ/見積もり進捗にはentryIdを加え、別の曲の見積もりを対象曲へ表示しません。実行中ジョブの見積もりはリスト・登録曲・形式・動画画質が一致するときだけ表示します。各見積もり応答は画面世代と選択変更世代を照合し、画面切り替え後に到着した応答を破棄します。

## 階層を保持する選択UI（Step6-1）

追加先・リスト取り込みのTreeViewでは、選択できないリストも親子構造の中に表示します。名前とチェックボックスだけを無効にし、子を開閉する矢印は独立して操作できます。選択不可になった古いチェックは選択集合から外し、折り畳み・検索で見えなくなった有効な選択は保持します。検索時に自動で開いた枝も折り畳めます。親変更のParentPickerでも自分自身・子孫を削らず、検索結果に含めたまま選択を拒否します。

既存曲の追加元にもParentPickerを使用し、「ライブラリ全体」を親なしの選択に対応させます。選んだリスト直属の曲だけを表示する従来の範囲を保持し、チェックした曲の参照はリストID・登録曲IDで管理します。追加先では表示中の追加元と選択曲の全所属元を選択不可にし、親や兄弟、選択可能な子は残します。選択や追加元へ至る祖先は初回に開き、その後の利用者による開閉を維持します。

移動と追加の確定処理は既存の共通追加確認・移動APIへ委譲します。共通モーダルのフッターに補助操作用の領域を設け、移動ボタンを追加の左隣に配置し、次の画面を開くと補助操作を破棄します。出力方式のボタン・用途表示とmainの方式指定は下記のStep6-2で接続しました。

## 出力・取り込み方式のUI接続（Step6-2）

出力画面はライブラリ全体を対象とする従来の範囲を維持し、情報のみとDLデータ付きの二つのボタンを用意します。情報のみはPC・スマホ間の情報共有、DLデータ付きはPC間の保存データ込みの共有として、同梱内容を表示します。情報のみはJSONを標準とし、保存先選択でZIPも選べます。DLデータ付きはZIPです。スマホ専用UIや同期機能は含みません。

rendererはexportLibrary({ mode })を呼び、mainはlibrary-share.cjsのShareModeで検証して既存のLibraryArchive.Exportへ渡します。方式省略時のmediaは互換動作として保持します。出力先選択と書き込みの間もmainのガードを保持し、二重出力を拒否します。rendererは出力/取り込みの同時開始を防ぎ、キャンセル・失敗後に操作を戻します。出力済み形式・同梱/非同梱・不足件数を表示し、応答時に画面世代が変わっていればその画面へ結果を反映しません。

取り込み先・階層選択は従来のImportSelectionとコアの計画/確定処理を利用します。計画のmodeに応じた説明を表示し、情報のみのローカル曲は登録情報として保持した件数を完了時に示します。元の祖先は構造として残し、未選択の曲・兄弟を追加しない方針と、既存のID・メディア照合・ロールバックを保持します。選択画面へ移る前に元画面が閉じられた場合は、返ってきた取り込み計画を取り消します。

## プレイリスト総数の上限（Step7）

StoreのMAX_PLAYLISTS（999）とValidatePlaylistCountで、親・子・独立リストを合わせた保有総数を判定します。作成前・保存前・読み込み検証、ZIP内のリスト数、取り込み後の総数に同じ判定を使います。取り込みでは選択した内容だけでなく、構造を保持するための祖先と既存リストも数えます。上限超過データは起動時も専用エラーとして停止し、本体とバックアップを保持します。

追加先/リスト選択は999まで、単曲移動・追加先は元リストを除く998までです。曲数と追加組み合わせの10000件、URL一括入力の100件、ファイルサイズ等の制限とは独立させます。旧JSON、情報のみJSON/ZIP、DL同梱ZIPも同じ保有総数を適用し、選択を減らして再試行するときに元の取り込み計画を利用できます。

深い有効な階層を保有数と別の深さ制限で隠さないよう、TreeViewでは経路上の祖先IDを確認して循環を止めます。共有参照の別経路は描画でき、既存の2000描画行ガードは維持します。モデルで999段の末端選択と親検索を確認し、実Windowsでの大量リスト操作・描画の確認はStep11へ引き継ぎます。

## 再生元の経路と共通保存状態（Step8）

再生バーの経路は、current.playlistIdの所有リストをcurrent.queuePlaylistIdの再生範囲から辿り、「ホーム」を先頭に表示します。queueのtimeline.currentが現在の登録曲IDと所属リストに一致する場合は、その最新の再生範囲を使います。閲覧中のリストや同じメディアの別の登録先からは推測しません。共有親では範囲を通る経路を優先し、移動でその経路がなくなった場合は現在の所属まで辿り直します。状態・所有リスト・範囲が変わるまで経路をキャッシュし、進捗通知ごとの探索を避けます。

SavedStateとPaintSavedBadgeが、一覧・編集/DL画面・再生バーのラベル、補足、読み上げと保存種類を担当します。downloads.availableのURL/パートごとのvideo/audio集合で、「DL済み」「音声DL済み」「オンライン」を判定します。動画と音声の両方は補足で示し、ローカル曲と不足ファイルは独立した状態として扱います。current.sourceやofflineから保存有無は判定せず、再生バーの補足にだけ実際の再生方式を添えます。

保存一覧の通知は関連バッジと再生バーへ反映します。所有リストの移動・名前変更はstate/current-update、再生範囲の変更は一致したqueue通知から追従します。読み込み中と一時停止を経路へ添え、停止時は保存バッジを消します。経路・曲名はtextContentで設定し、省略した経路もtitleで全文を参照できます。同じバッジ文言は繰り返し設定せず、ライブ領域での過剰な読み上げを避けます。

## プレイリスト中心のホーム（Step9）

home-view.jsのPageは、スナップショットと閲覧経路・ページ番号から、直属の子または最上位のカード情報だけを返します。既存のRoots/Ordered/RawWalkを利用し、子の最上位重複を除き、同じ親子経路と兄弟順を保持します。共有する子は親ごとの経路で辿れます。曲数は自分と子孫の登録数で、共有子リストを一度だけ数え、全体再生の除外設定では表示から隠しません。データ・選択・再生順は変更しません。

カード情報と画像のDOMは1ページ24件に制限します。ページ外のカード画像を読まず、曲一覧のDOMやサムネイル・長さ取得をホーム用に生成しません。経路は各親子辺を検証し、移動・削除後は残った有効な祖先まで戻り、ページ番号を範囲内に補正します。画面の経路は末尾3階層とホームまでに絞り、省いた祖先名を補足に残します。既存の左ツリー・選択画面の開閉状態や2000行ガードは変更していません。

Renderは画像・名前を開くボタン、独立した再生ボタン、子リスト表示ボタン、全体再生の参加チェックを描画します。画像は既存のプレイリストiconを使い、未設定/取得失敗時はmusic.pngへ戻します。名前と経路はtextContentで設定します。開く操作だけが選択リストを変更します。カード再生は閲覧先を変えず、階層移動は選択リストやキューを変更しません。再生ボタンは既存api.playの範囲指定へ渡します。

app.jsはホームと既存workspaceの表示を切り替えます。ホーム中はネイティブ動画ビューを非表示にして音声と再生バーを維持し、曲一覧の追従・描画を停止します。リストへ戻ると既存プレイヤーと曲一覧を表示します。通知はホームの専用欄か従来のplayer-areaへ移し、通常の通知によるプレイヤー領域の縮小とbounds更新を維持します。初期の選択リスト表示は従来どおりです。全登録曲の検索結果UIは次節で扱います。

## ホームの全登録曲検索（Step10）

library-search.jsのIndex/PageはDOM・通信・ファイルに依存しない純粋な処理です。親子順に反復走査し、全プレイリストを一度ずつ調べ、登録曲IDと所有リストIDを保持します。開閉状態とincludeInAllを検索範囲へ適用せず、同じメディアが別リストへ登録されていれば別の行を返します。共有子自体を経路ごとに重複展開せず、経路はTree.Pathと同じ登録順の先頭を使います。循環・共有経路の増殖をvisitedで止めます。

曲名・動画ID・URL・パートと所属経路をNFKC/小文字/ひらがなへ正規化し、空白区切りの語をANDで照合します。経路文字列は曲ごとに連結せず所属リストで共用します。レンダラーはスナップショットの参照が変わった場合だけ索引を作り直し、入力とページ移動では再利用します。結果は1ページ50件で、10000登録まで末尾へ到達できます。検索の入力欄は結果DOMの外に置き、IME変換中には描画せず確定時に更新します。

再生はapi.play(所有リストID, 登録曲ID)へ渡します。全体再生の重複排除で別所属へ置き換えず、除外したリストも個別再生できます。所属リストを開く操作は既存OpenPlaylistへ接続し、再生を開始しません。検索中もホームの閲覧経路・カードページ・元スクロール位置とツリーの開閉集合を変更せず、解除時に復元します。件数変化で検索ページが範囲外になった場合は補正します。

結果のDL状態は既存PaintSavedBadgeで一覧/編集/再生バーと共用し、downloads通知で行を作り直さず更新します。サムネイルはホームを監視する独立したListArtworkを使い、見えている行だけ既存entryThumbnailへscope=*で要求します。同時2件、背景・モーダル中の新規取得抑止、検索解除/ページ変更後の遅い応答の破棄と既存の安全なdata画像判定を利用します。動画の実再生・保存・権限判定は従来のmainへ委ねます。

## 共通データ検証と端末側アダプター

library-data.cjsは保存形式/階層/メディア参照/999リスト/10000登録の検証を担当し、fs・path・Nodeの乱数APIを読み込みません。必要な登録IDの生成は呼び出し側から渡します。Store.ValidateLibraryは従来の公開関数を保ち、randomUUIDを渡す薄いアダプターです。library-share.cjsはこの共通検証へ直接依存し、Storeを経由して保存処理を読み込まない構造です。検証規則と保存形式は維持します。

playlist-icon-data.cjsは標準のatob/Uint8Array/DataViewで既存PNGの形式・署名・寸法を検証します。ファイル読み込みとElectronによる縮小は従来のplaylist-icon.cjs側へ残します。Queueは整数乱数の生成を注入でき、mainはNodeのrandomIntを渡すためPC版の暗号学的乱数による選択を維持します。注入なしの共通処理はMath.randomを使います。Cloneも注入された生成関数を保持します。

common-boundaries.test.cjsはNode組み込みモジュール・Buffer・process・DOMを与えないVMで、構造検証・情報のみ共有・取り込みID計画・検索・キュー・PNG検証を実行します。共通モジュールが端末APIを直接読み込むと失敗します。実際の保存/取得/再生/OS連携は従来の端末側に残します。

## 再生開始と復旧

新しい曲では先頭から再生し、回数の計測を開始する。動画URLは既存のまま保存する。キャッシュがある場合は指定モードに合う音声／動画を優先し、なければBilibiliの埋め込みを開く。初期画質はqn=16、メニューが遅れて作られる場合は最初の20秒だけ360pを選択する。ユーザーの画質操作で自動選択を止める。

取得できた動画詳細から正しいパートのCIDを補完する。現在と次の2曲の詳細をバックグラウンドで準備し、再生開始をネットワーク取得で待たせない。同時取得は2件、メタデータは200動画まで。連続スキップで取得待ちを増やさない。avからBVへ公式ページが正規化された場合も、取得済みのaid/bvidとパートが一致すると同じ曲として認める。

初期読み込みは12秒、再生開始後に進行しなくなった場合は15秒で復旧へ進む。健全な一時停止と終了は監視を止め、再開後に再び監視する。古い画面・別の曲・子フレームから来た通知は無視する。

復旧1回目では公式動画ページを同じアプリのWebContentsViewで開き、プレイヤー要素を画面内へ合わせる。元のキュー・曲・パート・再生位置・一時停止状態を保持する。復旧2回目は公式方式を作り直す。それでも失敗したら通知して止める。外部ブラウザーは開かず、再試行を無限に繰り返さない。手動再読み込みで新しい復旧機会を与える。

公式方式で実際に再生が進んだ動画は、その起動中に方式を記憶する。合集情報が取得済みなら同じ合集も優先し、失敗する埋め込みを各曲で繰り返す負担を減らす。公式ページ全体の表示ボタンと、自動復旧のプレイヤー表示は別の状態とする。公式側DOMの変更・通信障害・アクセス制限まで解消できるとは扱わない。

## 回数とシャッフル

キーはBilibiliの正規化URL＋パート、ローカル曲は取り込み済みfileName。曲名・プレイリストIDでは数えない。同じ曲を別リストにコピーしても同じキーを用いる。BVとavを混在させた別URLの登録、および同じファイルの再取り込みは別キーとなる。

連続した再生位置の増分を時計の経過と照合して、実再生3秒で1回だけ加算する。位置を飛ばした増分、停止、読み込み失敗は除く。短い曲は80%以上を実再生して終了した場合に数える。再読み込み・自動復旧は同じ回数計測を継続し、二重加算しない。

抽選重みはw=1/(1+count)。各候補に独立した乱数uを与え、`-log(u)/w`が小さい順へ並べる。OS由来の乱数を使用する。同じ回数なら同じ確率となり、回数が多い曲を完全に排除しない。確定済みキューは回数が増えても並べ直さない。1周内の重複、前曲へ戻る操作、末尾を次周から除く既存仕様を維持する。

履歴は実際に通った直近1000件。予定は残りの確定済みキューで、リピート時は最低3曲先まで先に確定する。UIはこれを読むだけで、曲を選んだり抽選したりしない。手動スクロールしていない間だけ表示を次の曲へ合わせる。

## 保存と境界

動画はH.264で720p以下から高い画質、音声はAACで192kbps以下から高いビットレートを優先する。360/1080指定にも対応し、該当形式がなければ取得可能な近い形式を選ぶ。FFmpegで音声・映像をコピーしてMP4/M4Aへまとめ、再圧縮は行わない。したがって出力サイズは配信データに依存する。

1ジョブを逐次実行し、APIの認証・レート制限でジョブを止める。CDNのリダイレクト先も許可済みHTTPSホストへ限定し、1ストリーム8GB上限、通信停止60秒、中止時の削除を扱う。FFmpegへ渡すのはローカルのステージングファイルだけ。合計時間の差が3秒または2%を超える場合は完了扱いにしない。

既定はFavecusPlayer/downloads。カタログのキーはURLと形式のSHA256。パス・実体・サイズを確認し、保存先を逃げる参照やシンボリックリンクを拒否する。独自プロトコルは再生中のトークンだけを配信する。同じ形式の古い画質は、新データとカタログを確定してから片付ける。保存カタログ破損時には元データを保持して別保存先を要求する。

## 階層・UI

通常検索は畳まれた子孫も探索し、検索前の開閉状態を変更しない。親選択の検索は完全なツリーを残して該当箇所へフォーカスする。追加先は検索で隠れてもチェックを保持する。全一覧は保有リストを一度ずつ並べる。全体再生の参加フラグは子孫へ効くが、別の有効な親からの参照は別経路として扱う。

画像は64pxのPNGとしてプレイリストのiconへ保持し、左ツリーだけ描画する。曲ドロップの追加は既存の重複レビュー、移動は原子的なStore.Transferへ接続する。確認を閉じた場合は変更しない。

キー入力は通常画面とメディアpreloadで受ける。メイン側でも前面・非最小化・モーダル非表示を確認する。グローバルOSフックは使わない。入力欄・IME変換・設定・ドラッグ中は再生へ渡さず、次曲／前曲／切り替えの長押しは抑える。

## 0.6.1の修正理由

- 保存はNodeのfetchを使う専用経路へ分離する。Bilibiliセッションから取得したCookieは既知のAPIエンドポイントにだけ付け、CDN・画像には送らない。自動リダイレクトを禁止し、配信先の許可確認と認証・制限への停止を維持する。
- プレイヤー破棄は参照解除・世代更新を先に行う。closeが同期的にfocus等を発生させても旧WebContentsへsendしない。破棄されたsenderFrameへのアクセスは安全に失効させ、復旧の上限後は失敗したビューを閉じる。次曲・手動再読み込みは可能な状態を保つ。
- 配布版の診断ログはruntime/logs内に512KiB程度の2世代で保持する。動画ID・パート・復旧理由を記録し、Cookieや認証URLを記録しない。提示された警告はランチャー由来だが、実際に異常終了したプロセスの原因は再現できていない。
- 全リストの手動順は配列への追加順ではなく、親子グラフをたどった順にする。全体再生の参加判定とは分離し、空・除外・共有も表示対象にする。見出しの登録数と実際の再生対象数を区別する。
- サムネイルは完了カタログに相対パスとサイズを保存する。最大3MiBで画像の署名も確認し、破損・不足画像は再実行で補完する。画像保存失敗はメディア成功を取り消さない。保存済みの再生時は画像もローカルから読み、動画形式・音声形式・av/BV別名を解決する。
- ランチャー設定はruntime/configへ集約し、新旧双方の設定とEXE・appを同一更新で復元できるようにする。ネイティブランチャーは新しい場所を優先し、旧active.txtを読み取る互換経路を持つ。
- Discordはsmall/largeの選択に応じて楽曲画像と共通画像を割り当て、楽曲画像のURLだけにパート付き動画URLを設定する。details_url・buttons・共通画像のURLは設定しない。カード背景を指定したかのような表示や説明は行わない。

## 0.6.2の追加責務と判断

- download-estimate.cjsは配信情報だけで容量を見積もる。事前にメディアを取得しない。全ストリームのsizeまたはbitrate×durationを用い、画像・結合・コピー用の余裕を足す。欠測値は未確定と表示し、API制限では連続取得を止める。初回時間は10〜100 Mbpsの幅、開始後は全曲分の実測から計算する。見積もりID・対象ハッシュ・有効時間を照合し、古い選択で開始しない。
- offline-archive.cjsは完了データの同梱と選択復元を担当する。元URLを維持し、選択リストに対応する動画・音声・画像だけをコピーする。コピー完了後にカタログを確定し、Store保存に失敗したらカタログと追加ファイルを戻す。カタログで絶対パスや任意の展開先を受け入れない。
- zip.cjsは小さいアーカイブの従来ZIPを維持し、大きいサイズ・オフセットはZIP64へ切り替える。メディアを全量メモリへ読まず、CRCとサイズをストリームで確認する。上限1TiB・60000項目。
- 保存場所はプレイリスト／曲／形式ごとに整理する。既存配置は元データを保持したハードリンク、非対応環境ではコピーで新しいパスを作り、カタログ確定後に旧パスを片付ける。失敗時に元データを失わないため、先に移動しない。
- releases.cjsは公開GitHubリポジトリのlatestを読み、数値のバージョン比較とリリースページURLを返す。認証情報は要求しない。自動EXE実行・公開操作は行わない。
- ランチャーのRunはDWORD終了コードを符号なしのままI64で返し、CreateProcess失敗の-1と分離する。FP-LAUNCH/FP-EXIT、起動回の記録ID、ログパスを表示する。原因未確認の終了をファイル破損と表示しない。
- 再生Viewを切り離した後、次のイベントループでcloseする。閉じるまで参照を保持し、IPC処理中の破棄を避ける。同じ再生元のローカル曲・保存済み曲もViewを再利用する。
- Setupの保存先判定をinstall-coreへ集約し、すでに製品フォルダーなら重ねて名前を追加しない。プログラムだけの二重配置はruntimeへ保管し、失敗時に戻す。ファイルを含む未知のフォルダーは整理対象にしない。
- Maintenance、設定、ロックはruntime/config以下。既存デスクトップショートカットは対象アプリへのリンクを確認し、必要な場合は移動後の起動先へ更新する。

Discordの公開APIには四隅・任意ピクセルサイズ・カード背景指定がないため、動作しない設定を設けない。メイン画像／補助画像の選択と画像リンクだけを提供する。

## 0.6.3の異常終了対策

FP-EXIT-FFFF7003はCrashpadの未登録クライアントを示す終了値で、元の例外やGPU・メモリー不足などを区別する値ではない。警告から原因を断定しない。

- LoadEntryは世代と要求番号を先に更新して旧通知を無効にし、setImmediateでIPC／ネイティブイベントから抜けた後に画面を操作する。同じターンの連続操作は最新の要求だけを読み込む。すでに読み込み中の通信を待つ直列キューは使わず、次曲を待たせない。停止・アプリ終了では要求番号を進めて保留処理を失効させる。
- CloseViewはアクティブ参照を先に解除する。removeChildViewもcloseと同じ遅延処理へ移し、破棄は一回に限定する。取得済みのWebContentsを保持し、close後にundefinedとなり得るview.webContentsを再取得しない。予期しないdestroyedと遅延破棄が重なっても、Viewの切り離しが完了するまで保持する。
- crash-diagnostics.cjsは単一起動のロック取得後、最初のウィンドウ作成前にCrashpadを初期化する。uploadToServerはfalse、送信先URLは設定しない。起動IDと版番号を全プロセスの記録へ付ける。保存先はruntime/logs/crashes、Chromium警告・エラーはelectron.logへ保存する。初期化に失敗してもアプリ全体を止めず、diagnostics-startへ失敗を記録する。
- 再生診断にはプロセスのメモリー使用量も付ける。ネイティブ記録には直近のイベント・世代・曲ID・操作を短い注釈として付ける。JSONへCookieや署名付きストリームURLを追加しない。minidumpはプロセスのメモリー断片を含む場合があり、端末内で保持する。

参照: [Crashpad終了コード](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/crashpad/crashpad/util/win/termination_codes.h)、[Electron crashReporter](https://www.electronjs.org/docs/latest/api/crash-reporter)、[Electronログ指定](https://www.electronjs.org/docs/latest/api/command-line-switches)。


## フレーム切り替え中のIPC

受領ダンプ8件は同じWebFrameMainコンストラクターで停止していた。照合結果はCRASH-064.mdに記録する。WebContentsが生存しているだけでは、その内部のフレームが操作可能とは限らない。sendは内部でmainFrameを参照するため、try/catchだけではネイティブのCHECK停止を防げない。

MediaChannelは初期状態を送信不可とし、曲変更要求・主フレームの文書ナビゲーション・破棄・レンダラー終了で送信を止める。プレイヤーでは要求中のURLと一致するdom-readyの後だけ再開する。読み込み中もネイティブのミュートは可能で、音量・キー設定は最新値を準備完了後に送る。読み込み中の再生／一時停止は最後の切り替え状態だけを保留し、停止・別曲要求で破棄する。iframeや同一文書内の移動は現在の送信状態を変えない。検索画面とアカウント画面のメディア操作にも同じ制御を使う。

同じ再生方式のWebContentsViewは引き続き再利用する。曲切り替えごとの新しいレンダラープロセスや固定の待機時間は追加しない。画質・音質、保存・プレイリスト形式、GitHub更新設定はこの修正で変更しない。

## 0.6.6の階層と保存開始

Rootsは子として参照されるリストを最上位表示から除き、保存されている参照は保持する。Selectionは選択リストの子孫を内容対象とし、全祖先を空の容器として残す。無関係な兄弟や祖先の曲は含めない。取り込み分と既存データの親子グラフを保持し、メディアは動画・パート単位の共通保存先へ配置する。失敗時はカタログ・グラフ・追加ファイルを戻す。

祖先と子孫の重なった参照選択は最上位の選択枝だけを接続し、中間の親削除では同じ親・位置へ子を引き継ぐ。展開した別リストの曲へのドロップはtargetIdとafterで挿入位置を指定し、同曲があれば既存行を再配置する。

保存開始は見積もり完了を必須にしない。未完了の事前確認を中止し、最大3ワーカーの配信情報をLiveEstimateへ渡す。確認済みの容量と長さから残りを推計し、全件確認で取得を待たせない。完了済みデータは今後必要な空き容量から除き、各曲の保存前にも空き容量を確認する。

更新画面はHTTPSのGoogle Drive URLを保存して開く。旧GitHub設定を残すがアプリの更新確認では使用しない。新しい共有方式とGitHub公開は保留する。
